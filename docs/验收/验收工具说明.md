# 项目验收工具与当前证据边界

本目录记录可重复验收流程。工具输出会明确区分真实 HTTP 审查、合成容量测试、尚未开展的独立人工金标评测，以及尚未开展的正式基准。容量通过不等于法律准确性通过，权重存在也不等于模型已经成功推理。

## 独立人工标注

`tools/acceptance_annotations.py init` 从经授权的 UTF-8 TXT 生成 JSONL 待办。提供的示例是合成流程样本，`status=unlabeled`、`annotations=[]`、`reviews=[]`，没有填造标注人或自动补标。

另已生成 `docs/验收/待标注包_v1`：18份新编合成候选、6种合同类型、A/B两路独立盲标空文件和空仲裁模板。所有记录均为 `unlabeled`、`gold_ready=false`，不含规则答案或虚构标注人。详见包内README及hash manifest。合成候选不能宣传成独立采集的真实业务测试集。

每条记录保留原文 SHA-256、来源、同源 group_id、采集时间和授权依据。实体、风险及法条关联以原文字符 `[start,end)` 和精确 evidence 定位。两名独立人员在不查看系统预测的条件下分别标注，填写真实 reviewer_id、时间、manual 方法、decision 和各自标注版本 hash；随后仲裁人记录最终 annotations hash、时间和理由。空 annotations 可以表示经过人工确认不存在目标，但仍须完整复核和仲裁记录。

`validate` 检查 schema 核心字段、原文和跨度、人工审计链、跨 split 归一化原文重复、同源分组重叠、外部训练清单重叠。该校验不能认证人员真实身份、标注质量或发现所有转述/近重复；发布前仍需人工进行近重复检索和独立数据来源审核。

`freeze` 必须提供项目训练/开发来源清单，按 group_id 用固定种子划分 train/dev/test；只有全部仲裁完成且校验通过才生成冻结 JSONL 和 SHA-256 manifest。任何文本、标签或划分修改都应发布新版本；测试集不能参与阈值选择、提示词优化或模型训练。禁止把网页人工复核记录自动当成盲标金标。当前没有独立人工仲裁数据，因此不得报告独立金标准确率或 F1。

示例命令（使用实际 Python 完整路径，以下简称 python）：

```powershell
python tools/acceptance_annotations.py init --input-dir docs/验收/待人工标注样本 --out docs/验收/unlabeled_samples.jsonl --permission "合成流程样本" --origin "项目验收工具合成文本，不是外部测试集"
python tools/acceptance_annotations.py validate --data docs/验收/unlabeled_samples.jsonl --out tools/acceptance_results/annotations.json
python tools/acceptance_annotations.py freeze --data PATH_TO_ADJUDICATED.jsonl --training-inventory PATH_TO_COMPLETE_TRAINING_INVENTORY.jsonl --out NEW_VERSION_MANIFEST.json
```

## 正式 LawBench / ProvBench

`tools/acceptance_official_benchmarks.py` 只调用本地正式仓库中未修改的官方 Python 评价器。manifest 需要官方仓库/论文协议来源、核验人及时间、git commit、数据与预测文件 SHA-256、官方 split 与任务 ID、条目数、模型 revision/权重 hash、配置 hash、评价脚本 hash 和参数。已有项目 `lawbench.py` 是自建任务的 LawBench 式对齐，不能作为正式 LawBench 成绩。

LawBench 已核验官方 `open-compass/LawBench` README及原版 `evaluation/main.py`，固定commit为 `e30981bb3ff54c41571f222e0b23e92d27375388`。通过官方Git Tree API及immutable raw URLs取得79文件、36648470字节的稀疏源码快照，逐文件核对官方Git blob SHA-1与SHA-256；快照明确不是伪造的git仓库。原版zero_shot与one_shot各20任务，每任务500条，共20000条已就绪，manifest为 `verified_primary_source / data_ready`。真实模型全量预测和正式全量分数仍未开展。

专用入口 `tools/acceptance_lawbench.py` 支持官方数据plan、真实HTTP逐条推理、配置与源数据校验续跑，以及按官方工作目录调用未修改的main.py；官方指令已含one-shot示例时直接使用，不自行另造示例。参考答案只保存到官方输出refr字段，不拼进当前测试问题。详情见 `LawBench适配运行说明.md`。官方任务1-1是ROUGE-L，1-2是Accuracy，不使用自造精确匹配替代。

ProvBench已由ACL2025官方论文`2025.acl-long.312`及完整PDF核验，真实代码脚注是`https://github.com/labpaper/ProvBench`。本次该仓库及main/master README均HTTP404，属于公开可用性缺口，不能再描述为身份不唯一。论文§5.2（印刷页6245、PDF第6页）规定命中式R@1/3/5、Top-3 EM及基于黄金top-3的关系检测；overall F1未明示averaging，不能用MRR/NDCG或自选F1冒充正式指标。新增`acceptance_provbench.py`提供来源核验、严格本地交换格式、可执行论文指标诊断和固定官方checkout运行入口；合成计分fixture与8项护栏测试通过，但不称为原版评分器或模型成绩。正式`not_run`的具体缺项为真实官方数据/候选库/划分/版本、原版评价代码及实际预测，详见`ProvBench适配运行说明.md`。

```powershell
python tools/acceptance_official_benchmarks.py check --manifest docs/验收/LawBench.manifest.json
python tools/acceptance_official_benchmarks.py run --manifest YOUR_VERIFIED_MANIFEST.json --out NEW_OFFICIAL_RESULT.json
```

## HTTP 全流程与耗时

`tools/acceptance_http.py` 默认启动全新、隔离、关闭大模型/NER模型的真实服务器子进程，经 multipart 上传真实字节并实际运行审查，核对完整归档原文、图、trace、分页检索、pending 人工复核持久性及持久队列上传到完成归档。测试输入明确为合成合同，不能用于准确性评估。

分别记录进程启动到 health、首个审查请求、稳态不同长度和模型配置的 p50/p95；客户端总耗时从上传前到收到完整已归档响应，包含网络传输和归档，服务端 timings 单列。进程冷启动不声称清空操作系统/GPU/外部模型服务缓存。默认 5 个稳态样本的 p95 是小样本经验分位数，不是 SLA。

模型验收可对专门配置的大模型服务器显式传 `--base URL --llm on`；工具记录 observed 模型配置与逐份报告 stats，health enabled 只能证明配置，不能代替实际成功模型调用证据。默认离线结果不声称完成 8B 模型验收。

本次另有真实BERT/rule HTTP单例通过，客户端上传至归档响应4.746秒、LLM关闭，证据为http_deep_bert.json。真实8B CPU单token探针首次63.346秒、暖态59.792秒；该结果仅证明一次实际token生成及传输，因长度停止，既不验证法律质量/JSON，也不代表完整合同性能。当前CPU路径不具实用吞吐，GGUF运行准备另行记录。完整8B审查和正式基准尚待真实执行，不把加载成功当作推理验收。

```powershell
python tools/acceptance_http.py --samples 5 --lengths 500,3000,10000 --out tools/acceptance_results/http_offline.json
```

## 完整报告及持久队列容量

`tools/acceptance_scale.py` 默认 100000 条完整合成报告和 100000 个合成队列任务。归档采用实际 workspace schema，批量写入包含完整原文/blocks/clauses/elements/graph/trace 的 JSON，保留 512、2048、8192 字符分布和实际 payload 字节统计，随后通过真实 HTTP 核对抽样完整 payload、首末分页及名称检索。批量 SQLite 写入不等于 100000 次 HTTP 上传或审查。

队列使用独立 SQLite，调用真实 QueueStore.add_many 持久写入，重开读取、抽样 claim/complete、短租约恢复、取消与重试；没有启动模型 runner。模拟 complete 不创建真实审查报告。两个库隔离，API worker 不会拿到合成容量任务。输出 `contracts_reviewed=0`、`model_calls=0`，不可宣传“已审查十万份合同”。

最终容量复测使用新out、新归档库及新队列库，结果scale_100k_final.json：完整归档十万条8.685秒，8次HTTP读回p50/p95为0.290/0.365秒；独立持久队列十万项入库4.144秒、100次模拟调度1.135秒，租约恢复/重开/取消重试均通过。旧scale_100k.json保留；测量起始的全部产品Python及webUI源码hash记录在provenance中。

```powershell
python tools/acceptance_scale.py --count 100000 --dispatch-sample 100 --out tools/acceptance_results/scale_100k.json
python tools/acceptance_tests.py
```
