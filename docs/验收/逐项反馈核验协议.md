# 逐项反馈核验协议

`nodes._llm_logic` 的法条反馈使用 `bound-item-verifications-v1`，主体事实反馈使用 `bound-subject-fact-verifications-v1`，同时存在时记为 `mixed-bound-item-verifications-v1`。法条与事实分别分批调用，不将主体事实伪装成法条。普通、没有反馈项的审查调用继续使用既有 `defects` 协议。

## 输出与绑定

反馈调用必须返回 `verifications` 数组。每个本批 `feedback_item_id` 恰好对应一条记录：

```json
{
  "verifications": [{
    "feedback_item_id": "输入反馈ID",
    "candidate_id": "输入候选风险ID",
    "article_uid": "输入法条ID",
    "verdict": "confirmed",
    "reason": "逐项核验的理由",
    "clause_quote": "本窗口该反馈所涉及条款的原文片段",
    "article_quote": "该反馈绑定法条文本的原文片段"
  }]
}
```

ID 必须与输入逐字一致。条款引文必须出现在本窗口实际发送、且属于该反馈 `clause_ids` 的文本中。法条引文必须出现在同一 `article_uid` 所绑定的输入法条文本中。定位只忽略空白，保留标点；省略号、改写、其他条款或其他法条的引文不能通过。

反馈任务使用独立系统提示词：法条只有 `verifications` 根数组，主体事实只有 `subject_fact_verifications` 根数组，不叠加普通审查的 `defects` 输出示例。理由限40字符，各连续引文限80字符，避免把完整输入反复抄回。

在已核实的本机 llama.cpp 服务上，启动器自动启用 `ZLQL_LLM_NATIVE_JSON_SCHEMA=true`。每批发送实际根字段、必填项、当前ID枚举、长度和数组上限的原生JSON Schema；审计记录是否发送及schema的SHA-256，不保存schema正文。其他通用兼容网关默认关闭。显式schema遭拒绝时按失败记录，不静默取消约束后宣称成功。候选与法条配对、引文、缺项、来源和pending仍由业务校验器独立检查；schema保留 `needs_manual`，不强迫模型确认。

原生反馈的合同引文采用提取式约束，报告显式标记 `clause_quote_mode=native_source_extract_selection`。只从当前批绑定条款与实际窗口的交集中，提取最长80原字符的连续片段；长片段以40字符步长重叠覆盖到尾部，不拼接分段、不改写原文，模型只能从这些片段中选择 `clause_quote`。其他法条／事实／来源引文继续独立验证。此方法解决模型把法条复制进合同引文字段的问题，证明选中片段来自已发送合同；它不证明片段相关性、法律真值或模型自由生成引用的能力。结论和理由仍由模型给出，`rejected`、`needs_manual`均保留；某项选中其他项的来源仍会被逐项验证器拒绝，没有可用合同来源时保持pending。

`verdict` 只允许：

- `confirmed`：模型认为反馈判断有依据；
- `rejected`：模型认为反馈判断不成立；
- `needs_manual`：模型无法完成判断，保留待核验。

前两种只有在 ID、理由、双引文、来源完整性以及输出完整性全部通过时才计为已完成。`rejected` 不会直接删除已有风险。`needs_manual`、空 `defects`、缺失记录、重复记录、未知 ID、错候选、错法条、错引文、空理由、非法 verdict 或截断输出，都不能自动形成成功的反馈覆盖率。

## 来源截断与覆盖率

每批至多 3 个反馈项，同时受 4000 字符的反馈上下文上限约束。所有项分批排入计划，预算耗尽、异常超长、未匹配窗口或未执行项均显式保留 pending。

反馈法条文本最多发送 1000 字符。输入已声明截断，或本层实际发生截断时，即使模型给出 `confirmed/rejected`，结果也标记 `verified_scope=sent_excerpt`、`article_source_complete=false`，以 `article_source_truncated` 保持 pending；不能把局部引文当全文法律关系核验。未报告截断时，作用域为 `bound_provided_text`，也只针对提供的文本，不代表自动核实了法条版本、效力或外部事实。

每个调用记录 `verifications`、`verification_errors`、`verified_feedback_item_ids` 与 `uncompleted_feedback_item_ids`。总诊断包含协议版本、全局已完成/待核验 IDs，以及批次和窗口状态。同一反馈出现在多个相关窗口时，必须在每个相关窗口完成合法核验，才能形成全局完成状态。普通正文覆盖、显式引用依赖覆盖与反馈完成分别保留，不能相互替代。

报告中的反馈调用另保留 `feedback_response` 诊断快照：原始两个typed根的有界JSON字符串、原始与保留行数、长度及截断标记，最多16000字符、本批数量加1条异常记录。它用于查看被拒绝的实际引文；校验仍使用未经改写的模型返回值，快照不进入模型调用SQLite审计库，也不作为截断结果的通过依据。

当前指纹的模型结论会按反馈ID与候选ID／alias关联到具体风险的证据链，保存原始verdict、理由、引文、错误及当前状态；`model_feedback`证据强度为0，不用于抬高风险置信度或改变评分。合法的`rejected`及跨窗口意见不一致可完成执行协议，但仍推动人工复核；缺项、错绑及`needs_manual`同样进入对应风险的人工队列。协议完成与法律结论确认分开，`confirmed`不清除其他待核验原因，也不自动删除或确认既有风险。旧指纹只留历史审计，不放行新证据。

## 主体事实与来源反馈

节点③的 `fact_checks` 和逐请求 `verification_results` 实际进入节点②的 `subject_fact_feedback`。每条绑定主体、事实ID、来源ID、事实类型、候选及条款ID，并附上 `fact_evidence_text`、`source_evidence_text` 和来源元数据。模型必须返回独立的 `subject_fact_verifications`：

```json
{
  "subject_fact_verifications": [{
    "feedback_item_id": "输入反馈ID",
    "fact_id": "输入事实ID",
    "source_id": "输入来源ID",
    "subject_name": "输入主体名",
    "fact_type": "输入事实类型",
    "clause_id": "输入条款ID",
    "verdict": "needs_manual",
    "reason": "给定材料尚不足，需要补充证据",
    "clause_quote": "对应条款连续原文",
    "fact_quote": "fact_evidence_text连续原文",
    "source_quote": "source_evidence_text连续原文；没有来源时为空"
  }]
}
```

事实反馈每批1项。各ID、主体、类型及三类引文分别匹配，缺失、错绑定、改写和输出截断不能计完成。unknown、冲突证据、来源不完整、证据截断、上游请求pending或 `needs_manual` 均保持pending；这些事实批次产生的缺陷在证据未解决时被屏蔽，不能把缺证转为违法风险。

完全没有来源的四类默认unknown，按主体及对应条款合成 `unresolved_subject_checks`，保留各类 `check_states`；`missing-evidence:` 前缀与 `record_provided=false` 表明这是缺证状态，不是外部已知事实。有证据的 `fact_id` 和④发来的核验请求仍逐ID独立处理。无法映射到有效条款的反馈列入unmatched，不回退为任意全文。

事实、来源或上游请求结果变化会改变反馈指纹，重新触发核验。主体和法条反馈共同进入 `feedback_items`、已完成/待核验ID账本；原失败尝试保留，当前待核验项阻止假稳定。`pending_subject_verification_request_ids` 单独保留尚未解决的上游请求，即使模型给出confirmed也不能抹掉它们。

## 能力边界

这里验证的是模型确实逐项回应，以及回应的 ID 和引文可以绑定、定位到提供的原文。它无法单凭结构与引文检查保证法律判断为真，也不能代替专业人工复核。测试使用隔离合成 fixture 验证协议边界，不是人工法律金标成绩。

```powershell
.\.venv\Scripts\python.exe -m unittest zhilv_qiling_v2.tests_v2.test_feedback_verification_protocol zhilv_qiling_v2.tests_v2.test_subject_fact_feedback zhilv_qiling_v2.tests_v2.test_feedback_retry zhilv_qiling_v2.tests_v2.test_core_completion -v
```
