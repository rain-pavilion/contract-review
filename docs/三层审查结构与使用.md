# 工作流、审查点与评估结果

项目现在以三层结构组织合同审查，主体审查是其中的一个审查领域。三层记录由引擎产生并随报告保存，页面不根据风险数或评分推导审查通过。

| 层次 | 本项目记录 | 查看位置 |
| --- | --- | --- |
| 工作流 | 审查背景、解析、要素与逻辑分析、主体与法条核验、综合评估、人工复核的实际执行状态与门槛 | 高级工作台“工作流”及资料库报告 |
| 审查点 | 独立的问题、判断标准、负责节点、所需证据、适用范围与版本 | “审查点” |
| 评估结果 | 本次问题或执行情况、可能影响及其依据、建议、原文证据、关联风险和待办 | “审查点”的逐项结果及“评估结果” |

## 如何使用

1. 在合同库打开高级审查工作台，上传文件或粘贴正文。
2. 选择合同类型和审查立场。默认自动识别类型、中立审查；人工指定类型优先，同时保留文本识别的类型。甲方/乙方立场以原文身份为准，不表示身份或签约授权已经核实。
3. 执行审查，分别查看工作流门槛、逐点标准和本次发现。类型或立场改变后应重新执行；内容标识仍绑定原文件名和全文，审查上下文另有指纹。
4. 在证据、原文和人工复核页面核对发现并记录处理意见。批量、合同包及资料库任务沿用提交时保存的类型和立场，重启后保留。
5. JSON 与 Markdown 保留三层内容。旧归档未保存该结构时明确显示“未保存三层审查记录”，不补造历史执行。

命令行的 `review`、`batch`、`explain` 使用相同字段，例如：

```powershell
.venv/Scripts/python.exe -m zhilv_qiling_v2.cli review samples/tech-development-contract.txt --contract-type 技术开发 --review-position party_b
```

HTTP JSON、query 与 multipart 字段为 `contract_type` 和 `review_position`；类型允许 `auto` 及页面列出的合同类型，立场允许 `neutral`、`party_a`、`party_b`。不支持的值会被拒绝，不会悄悄退回默认值。多种来源同时提供选项时，query 覆盖 JSON，multipart 表单覆盖 query。

## 六节点与工作流的关系

六个核心节点仍是：①主脑规划与调度、②要素抽取、③逻辑审查、④主体审查、⑤法条匹配、⑥综合评估。②负责信息抽取、③负责上下文及跨条款处理，两者为并列职责；当前执行器顺序调度。三层结构是记录任务、标准和结果的方式，不要求每个审查点占用一个新智能体，也不要求六个节点各加载一份大模型。

主脑、逻辑审查及综合评估的实际模型输入包含本次类型与立场。逻辑审查请求还带入该节点负责的审查点问题、判断标准及版本；结果仍须通过既有引文和证据规则，不能凭模型声称已完成而将所有点判为通过。既有模型池、预算、确定性评分和未完成任务账本继续生效。

## 当前检查覆盖与状态含义

审查点目录包含14个领域：主体身份、签约授权、经营资质、权属权限、价款、付款条件与期限、交付、验收、责任安排、法律适用、争议解决、跨条款一致性、保密、合同标的与范围。

**目录定义不等于14项已经全面自动化执行。** 既有规则、风险及证据记录映射到相应审查点；没有具体执行记录的审查点保留“尚未执行”，不得以零风险或高分推定通过。人工核实要求与发现状态独立保存，发现问题的同时也可能需要人工确认。

新增的付款期限规则仅筛查所给文本中的直接付款句：

- “验收合格后支付尾款，具体付款期限另行协商”形成带原文的问题线索与补充期限建议。
- “验收合格后10个工作日内支付全部尾款”只可形成该有限文本规则的“限定范围内未检出问题”，不能证明完整付款安排合理或法律结论成立。
- 开票期限不能代替付款期限；分期中的明确首款不能覆盖不明尾款；不确定触发条件、间接引用、附件、待填写内容及异常日期留待核实。
- 解析遗漏付款句、条款与全文不一致、OCR未确认等情况不能形成完整的否定检查结论。付款标题不被当成一笔缺期限的义务。

付款检查单独保存为执行凭据，不伪装成原有风险，也不额外改变原有风险评分。评估结果保留 `risk_ids`、`check_ids`、`clause_ids` 和解释记录引用，便于追踪实际来源。

## 保存的数据

引擎为两种审查模式都生成：

```text
stats.review_context       本次类型、检测类型、来源、立场、上下文指纹
stats.review_point_checks  实际执行的独立检查凭据
stats.review_framework
  schema_version = contract-review-three-layers-v1
  context
  workflow {stages, manual_required, pending_count, ...}
  review_points[]
  assessments[]
  summary
```

API 另将已经保存的 `review_context`、`review_framework` 透出到报告顶层；不改变旧报告的原始内容。每个评估结果保存执行范围、定位状态和未决原因，并明确 `legal_truth_established=false`。
