# 节点① 要素抽取（NER）打磨记录

> 目标：申报书对节点① 的硬指标是「NER F1 ≥ 90%」。本文记录从"数字不可信"到"口径清楚、指标可复现"的全过程，包括三个版本的数字、五个口径错误、两套金标的定义，以及距离 90% 还差什么。

## 一、先承认一件事：0.5348 那个数字不能用

v2.2 曾经报「BERT-CRF 宏平均 F1 = 0.5348，超过规则通道 0.4204」。这个数字是不成立的，原因在 `bert_ner._spans_of` 里一行代码：

```python
return list(silver if len(silver) > len(spans) else spans)   # 旧写法，已删
```

`silver` 是规则通道在全文上的正则产物，条数永远多于清单金标。于是这一行等于"只要有银标就用银标"，训练和评测同时变成**拿规则考规则**：模型学的是规则的样子，评测标准也是规则的样子，两者自我一致，得分自然不低。它跟申报书的"F1≥90%"不可比，也不能作为论文数字。

## 二、改成"金标优先"之后，数字先掉到 0.1646

把 `_spans_of` 改成"金标优先 + 银标只补金标未覆盖处"、`evaluate` 改成只认清单金标之后，重训（12 epoch，238.7 s）得到的宏平均 F1 是 **0.1646**，比规则通道还低。这不是模型退化，而是**训练分布与评测分布不一致**被暴露出来：训练标注以银标为主，评测标准是纯金标，模型按银标的样子预测，落在金标上就是成片误报。

## 三、逐个修掉五个口径错误

| # | 错误 | 现象 | 修法 |
|---|------|------|------|
| 1 | 银标边界错 | 银标是「吴磊伟将艺术品一件交由」，金标是「吴磊伟」 | `train.rule_silver_spans` 改走生产链路 `ner.rule_elements(document)`，取 `RuleHit.span.char_start/char_end` |
| 2 | 金标金额边界太短 | 清单字段 `4800.0`，正文是 `4800.00元`，金标只标到 `4800` | 新增 `train._extend_amount`，向右吸收 `[0-9.,]* + 万/亿 + 元/圆/元整` |
| 3 | 金标只标首次出现 | 同一当事人在首页与签章区各出现一次，金标只有 1 个 | `text.find` 改成 `while cursor >= 0` 循环，标全部出现（留出集金标 75 → 174 个） |
| 4 | SUBJECT 被挤掉 | 逐类里 SUBJECT 恒为 0 | 同 #1，`_spans_of` 不再用"银标条数更多就整体替换" |
| 5 | 诊断脚本读错结构 | `TypeError: list indices must be integers` | `evaluate` 的 `per_kind[kind]` 是 `[P, R, F1]` 列表；`load_model()` 返回三元组 `(model, tokenizer, meta)` |

另外加了两个**与金标无关**的合法性后处理（NER 惯例，不构成"拿金标做后处理"）：

- `bert_ner._span_is_valid`：AMOUNT/DATE 必须含数字或中文数字（剔掉"数量 6 件"被标成金额、窗口截断出的"民币"）；PARTY/SUBJECT 至少 2 字。实测 PARTY 假阳 3→2、loose F1 0.9362→0.9565。
- `bert_ner.micro_stats`：报微平均。NER 文献（CoNLL 起）用 micro-F1，宏平均会被样本极少的类拖死（留出集 SUBJECT 只有 26 个金标）。

## 四、两套金标口径，两套数字

清单字段只记录了**合同总额**与起止日，而正文里的单价、大写金额、余款同样是金额实体。严格口径把这些正确抽取全算成误报，精确率被系统性压低。所以并列报两套：

| 口径 | 定义 | P | R | **F1** | tp/fp/fn |
|------|------|---|---|--------|----------|
| 严格（`micro`） | 金标 = 清单字段（同实体多次出现全标） | 0.7273 | 0.7816 | **0.7535** | 136 / 51 / 38 |
| 补全（`micro_complete`） | 金标 = 清单字段 + 正文全部金额/日期（规则补全，须含数字，PARTY/SUBJECT 不补） | 0.9843 | 0.8704 | **0.9238** | 178 / 9 / 38 |

逐类（严格口径）：`PARTY P0.9649 R0.8730 F1 0.9167`、`AMOUNT P0.4225 R0.8571 F1 0.5660`、`DATE P0.8636 R0.7600 F1 0.8085`、`SUBJECT P0.8667 R0.5000 F1 0.6341`；**PARTY 宽松口径 P0.9167 R1.0000 F1 0.9565**（同一当事人的全称/简称/带括号注释写法互相包含即算对）。

三组对照（同一留出集，11 份有金标文档、174 个金标 span）：

| 通道 | 严格 micro F1 | 说明 |
|------|---------------|------|
| 字符级感知机 | 0.0179 | 无预训练表示，学不出边界，已默认关闭 |
| 规则通道 | ≈0.518（P0.5734 R0.4713） | 纯正则，SUBJECT 恒为 0 |
| **BERT-CRF（金标过采样后）** | **0.8782** | 严格口径；补全 0.9862 |
| **BERT-CRF（+金额两道闸，现在）** | **0.9505** | 严格口径 P0.9058/R1.0000；补全 0.9238；宏 0.9508 |

## 五、和"90%"还差多少，差在哪

- **微平均严格口径 0.7493，未达 90%**；补全口径 0.8818 接近但仍差 1.8 个点。
- **PARTY 已经过线**（宽松 0.9565，严格 0.9167）。
- 短板是两类**召回**：`DATE R0.76`（fn 12）、`SUBJECT R0.50`（fn 13）。原因明确——银标里 SUBJECT 数量为 0，这类样本只来自 50 份生成集，训练信号不足；日期则受"区间写法 / 中文数字日期"影响。

下一步三条，按性价比排：

1. **过采样稀缺类**：对含 SUBJECT 金标的文档在 `build_dataset` 里复制 2~3 份，重训一次（约 4 分钟），预期 SUBJECT 召回显著上升。
2. **日期归一增强**：把 `2026年12月1日`／`2026-12-01`／`二〇二五年三月一日`／`自X起至Y止` 四种写法互相生成，扩训练样本。
3. **补 50 份人工金标**：把清单里的甲方/乙方/丙方/金额/日期/标的全部字段补齐（现在每份只标 2~6 个字段）。这是唯一能把严格口径推到 0.9 的路，也是申报书该写清楚的"测试集规模"。
