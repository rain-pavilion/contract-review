# 跨条款与跨附件上下文审查

本轮在现有 `zhilv_qiling_v2` 审查链上补充“要素提取 → 来源绑定与图约束 → 组合检查 → 证据与推导回执”。图用于组织上下文和限定证据关系，审查规则负责判断具体组合是否形成问题线索。

## 在工作台使用

1. 沿用现有合同上传、文本输入或合同包审查流程。跨附件检查需要先通过合同包流程提供主合同及附件；单份文本只能核对本次实际提供的内容。
2. 完成一次新审查，在报告中打开“上下文审查”页签。旧报告不会自动补跑；缺少本轮记录时显示未记录状态。
3. 查看来源文档、图约束检查和组合发现。展开组合发现，可见实际发现、可能影响、处理建议、原文与来源、推导步骤、适用假设和待核原因。
4. 点击证据的原文定位按钮跳转到相应条款。Markdown 导出同时保留证据编号、原文、来源、字符偏移、原文指纹及推导依据。

组合发现并入现有审查点框架，仍需人工复核；不增加既有 `risks` 数量，不改动原辅助评分。

## 本轮实现的检查

| 检查 | 实现范围 | 保守处理 |
|---|---|---|
| 图约束 | 条款标识唯一性、原文引文与来源绑定、图关系端点完整性 | 重复标识、错误偏移、哈希不符或来源冲突保留问题记录；不使用失效引文作为可信前提 |
| 条款引用作用域 | 优先在同一来源内解析，支持明确指向附件的引用 | 不同附件的“第一条”不互相覆盖；未知附件或目标不唯一时保留悬空／歧义信号 |
| 显式前置条件循环 | 消费已提取的义务与前置关系，展示形成循环的原文 | 遇到相关否定、例外或优先条款，补充证据并转为待人工核对 |
| 金额关系 | 显式总额与预付款、尾款关系，以及同角色字面金额差异 | 不因金额相同就认定同一义务；跨来源或适用关系不足时保留人工待核 |
| 验收、测试与尾款时序 | 组合“最终验收后付尾款”“无异议视为最终验收”“最终验收必须包含测试及最早完成时间” | 核对标的、验收阶段、同一起算和日历单位；缺前提、否定、可选测试、OCR待核或优先约定不输出无条件确认 |

例如：主文约定“本设备最终验收合格后支付尾款”，附件一约定“收货后3日内未提出书面异议，视为最终验收合格”，附件二约定“最终验收必须包含性能测试，该测试最早在收货后第5日完成”。本轮规则可把三处证据连接起来，提示默认验收可能早于必要测试并影响尾款安排，同时保留“同一标的、同一最终验收、同一起算与单位”等适用前提。删除必要前提后，不再确认同一三证据组合。

## 状态如何理解

- `issue_found`：限定文本规则形成了问题线索，仍需人工核对适用范围及法律意义。
- `needs_manual`：存在缺证、否定、例外、来源质量或范围不明等事项，需要人工核对。
- `not_checked`：未形成可执行的本项组合，不代表该安排审查通过。
- 图约束的 `valid` / `scope_complete` 只描述本轮结构与绑定检查，不能推导材料已经齐全或合同不存在风险。
- 信息齐全性默认 `not_evaluated`，页面显示“未执行”；执行完成也只表示算法运行状态。

## 数据与接入位置

统一入口：

```python
from zhilv_qiling_v2.context_review import evaluate_contract_context

result = evaluate_contract_context(contract)
```

单智能体和多智能体通过 `ReviewEngine.run` 共用这一入口。报告保存于 `report.stats["contract_context_review"]`，API 同时提供顶层 `contract_context_review`，归档读回沿用同一结构。

返回记录的版本为 `contract-context-review-v1`，包括 `source_documents`、`proposition_graph`、`constraints`、`findings`、`checks`、`completeness` 和 `summary`。每条发现保留独立证据编号和推导前提引用。

证据的 `start` / `end` 为条款原文中的左闭右开字符偏移，`source_sha256` 绑定该条款文本；`original_sha256` 来自已有文件来源元数据，二者含义不同。原文与文件哈希绑定用于追溯，不能证明材料真实性。

## 预留的信息齐全性接口

用户尚未提供新的齐全性核对算法，本轮不自行推定核对清单。可通过以下签名接入后续规则：

```python
def check_information(contract, *, context):
    # context 是已完成上下文检查记录的深拷贝；在此接入业务规则。
    return {
        "status": "not_evaluated",
        "manual_required": True,
        "message": "待接入业务齐全性规则",
    }

result = evaluate_contract_context(contract, completeness_check=check_information)

# 在完整引擎中接入：
# ReviewEngine(config, completeness_check=check_information).run(contract)
```

回调返回 JSON 可序列化字典，显式状态为 `completed`、`needs_manual`、`not_evaluated` 或 `error`。异常及无效返回会隔离为齐全性执行错误，不中断已有组合审查，也不转成通过结论。该接口不允许宣称已自动确认法律事实。

## 验证与能力边界

本轮离线验证覆盖来源绑定、缺前提、不同标的／阶段、否定、优先与例外、OCR、引文篡改、重复标识、附件作用域、回调异常、单／多智能体接入、API归档、Markdown、页面转义与定位。浏览器另核对真实报告、导出和桌面／移动端布局。

规则采用有界中文句式与明确证据，不是通用合同语义推理器。复杂指代、隐含优先关系、未提供的附件、未覆盖的表述及实际履行事实仍需另行审查。工程测试通过不等于法律判断准确率已经得到验证。
