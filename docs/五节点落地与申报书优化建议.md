# 按申报书落地的五节点实现（v2.1）与申报书可优化点

> 目标读者：马宇轩（答辩与申报书修订）、后续接手代码的人。
> 本轮只做一件事：**把申报书写的五个节点按原意补回代码**，能跑、能降级、能验收；
> 同时把申报书里我认为写不实或写不准的地方列出来，附改法。

---

## 一、五节点落地对照

| 申报书节点 | 申报书写法 | 代码落点 | 状态 | 模型不可用时 |
|---|---|---|---|---|
| ① NER | 抽取当事人/金额/日期/标的，要素经"边"送到③④ | `ner.extract_elements` → `nodes.node_ner` | **已有且更强**（规则+感知机+双通道融合，`bbox` 定位） | 规则通道照跑 |
| ② 逻辑错误检测 | 调 LegalOne-8B 遍历推理 | `nodes.node_logic` = `rules.run_rules` + `detectors.run_detectors` + `_llm_logic` | **双通道已通**：规则 27 码 + 15 条检测器兜底，模型分支按条款批量问、**引文校验**后才收 | 规则通道照跑，记 `llm_off` |
| ③ 主体资格审查 | 法律知识图谱 + RAG，核验资格/权限/信用 | `subject_graph.check_subjects` → `nodes.node_subject` | **新增**：小图（主体-类型-资质-权限-信用）+ 5 条核验规则，结论带图上路径 | 纯规则，不依赖模型 |
| ④ 法条匹配 | 参照 PROVBENCH，BERT/Mamba 编码 → 余弦 → 多头注意力判"一致/冲突" | `retrieve`（三路召回+RRF+LTR） + `entailment.judge_pair` | **判别已补**：8 维判别特征 + 三分类弱监督逻辑回归，输出 entail/contradict/neutral | 判别器是本地的，照跑 |
| ⑤ 综合评估 | 调 LawBench 系统化评估 → 结论 → 人工复核 | `agents.score_risks`（确定性 0~100） + `nodes.node_judge`（模型写复核意见） | **分数永远规则算**，模型只写说明与"该人工看哪里" | 只输出分数与规则摘要 |

### ②③④ 互为输入怎么落的

```
节点① 要素 ──┬─► 节点② 逐条查缺陷 ──focus_clause_ids──► 节点③ 优先核验这些条款涉及的主体
              │                                              │
              │                                     query_hint（主体类型/所需资质/是否机关）
              │                                              ▼
              └──────────────────────────────► 节点④ 用 hint 收窄检索与判别
                                                             │
                                        contradict 的条文 ────┴──► 回灌节点②：给该条款挂
                                                                    `entailment_conflict` 证据
                                                                    并上调置信（+0.05）
```

回环有上限，全部走 `config`：`max_evidence_rounds` / `max_legal_retries` / `max_judge_retries` / `max_arbitration_rounds`（各默认 1），每次回环都写 `TraceEvent`。

### 三条写死在代码里的规矩

1. **模型不能造证据**：节点② 的每条模型缺陷必须带 `quote`，且 `quote` 必须在条款原文中出现（`_locate_quote`，允许省略号截断），否则整条丢弃并计 `rejected`；
2. **模型不能改分数**：节点⑤ 的分永远由 `score_risks` 算，模型只写 `summary` 与 `focus`；
3. **降级必须留账**：任何节点在模型不可用时把原因写进 `degraded`，最终进 `report.stats["degraded"]`。

## 三、申报书里有 8 处我建议改（附改法）

### 1. "NER F1 ≥ 90%"这个指标要写清口径

- **问题**：申报书只写 F1 ≥ 90%，没说是规则通道、模型通道还是双通道，也没说测试集规模。本项目实测：纯规则宏平均 0.42，感知机通道（CPU、无预训练）宏平均 0.0179，**同一批测试集上双通道融合后规则侧仍只有 0.42**。7B 模型在 113 份语料上也不会到 0.90。
- **改法**：写成"当事人/金额/日期三类 ≥ 0.90，标的类 ≥ 0.75，规则+模型双通道，测试集 ≥ 50 份人工标注"。这样既能达标，也不怕评委追问。

### 2. "用 LegalOne-8B 遍历推理每条条款"在时延上站不住

- **问题**：一份 24 条条款的合同 = 24 次请求；v1 用 Qwen2.5-7B 跑 28 条条款实测 **132.78 s**。8GB 显存跑 8B 模型，单份很容易超过"≤3 分钟"。
- **改法**：写成两段式 —— 规则/检测器先把候选缩到 6~10 条，模型只复核这些条款（默认 `llm_max_clauses=24`，可调）；并把"≤3 分钟"限定为"规则通道秒级 + 模型通道按需"。

### 3. 节点③的"法律知识图谱"必须交代规模与来源

- **问题**：申报书说"集成法律知识图谱与 RAG"，但没说图谱多大、数据从哪来。企业资质、失信名单都不在公开可离线数据里，答辩现场无法证明。
- **改法**：写成"**可扩展的轻量知识图谱**：本轮覆盖 11 类采购标的的资质要求、5 类签约权限线索、7 类信用负面线索，节点与边由 `QUALIFICATION_RULES` 等常量表定义，可按地区/行业扩充；待接入外部数据源后可替换为全量图谱"。现在的实现正好是这个说法。

### 4. 节点④"BERT/Mamba + 多头注意力"需要标注数据，建议直接采用 PROVBENCH 口径

- **问题**：判"一致/冲突"是监督任务，自建标注做不到 PROVBENCH 的规模（2698/404/448 条款对）。本机也没有预训练权重。
- **改法**：两条路二选一 ——（a）**采用 PROVDATA 训练**，报告 R@1 / 冲突检测 F1，与论文对齐；（b）**写成本轮的弱监督判别器**（8 维特征 + 三分类），并诚实写明"非 BERT 级语义判别"。我建议答辩用（b）讲思路、（a）讲后续，不要说"已实现多头注意力"。

### 5. "调 LawBench 评估"这个动作名不副实

- **问题**：LawBench 评的是模型的**法律知识记忆与推理**（法条背诵、案情分析），不是"合同审查质量"。用它评估本系统会被问"你的输出和 LawBench 的题怎么对应"。
- **改法**：LawBench 只用作**模型选型依据**（说明为什么选 LegalOne-8B 而不是通用模型）；系统效果改用**自建 113 份语料 + 10 份对抗样本 + 人工一致性**来报，本项目已有 R=1.000 / P=0.571 的实测。

### 6. "支持十万份级存储/检索"缺存储方案

- **问题**：申报书写了十万份级，但代码里没有持久化层（v1 的 qdrant 已移除）。评委问"十万份存在哪"会答不上。
- **改法**：写清"SQLite + 分页文件 + 倒排索引；向量检索为可选加速"，并说明当前 63 份真实合同的入库形态（`meta.json` + `pages/` + `text/`）。十万份是**容量设计目标**，不是已压测结果。

### 7. "需 GPU"与"≤3 分钟"要分层写

- **问题**：申报书说"需 GPU、可调 API 或本地部署 8B"，但"≤3 分钟"是按什么环境算的没写。
- **改法**：写成三档 —— 规则通道（无 GPU，0.02~0.36 s/份）、API 通道（网络往返，约 30~90 s/份）、本地 8B（8GB 显存，约 60~180 s/份）。这样"≤3 分钟"有环境前提，不会被抓。

### 8. 回环"②③④互为输入"要写终止条件

- **问题**：申报书说了互为输入，但没说什么时候停。评委常问"会不会死循环"。
- **改法**：照代码写"四个回环各设上限（默认各 1 轮），每次回环写 TraceEvent；收敛判据是候选集合不再变化或达到上限"。本项目的 `max_*` 参数就是这句话的实体。

## 四、接入真模型（三条路，任选其一）

```powershell
# A. 本地 Ollama（推荐先试，8GB 显存可跑 7B 量化）
ollama pull qwen2.5:7b
$env:ZLQL_LLM_ENDPOINT="http://127.0.0.1:11434/v1"
$env:ZLQL_LLM_MODEL="qwen2.5:7b"
$env:ZLQL_LLM_API_KEY=""

# B. vLLM / LMDeploy（有 GPU 时吞吐更好，接口同样 OpenAI 兼容）
python -m vllm.entrypoints.openai.api_server --model /models/LegalOne-8B --port 8000
$env:ZLQL_LLM_ENDPOINT="http://127.0.0.1:8000/v1"

# C. 云端 API（注意合规：合同正文属敏感数据，建议脱敏或走内网）
$env:ZLQL_LLM_ENDPOINT="https://api.example.com/v1"
$env:ZLQL_LLM_API_KEY="sk-..."

# 打开开关（三者都要）
$env:ZLQL_ENABLE_LLM="1"      # 或在代码里 Config(enable_llm=True)
```

验收三步：

```powershell
python -m zhilv_qiling_v2.reports.experiments.check_llm_channel   # 假端点自检（不需真模型）
python -m zhilv_qiling_v2.cli doctor                              # 看 llm 是否可用
python -m zhilv_qiling_v2.cli review samples\tech-development-contract.txt --trace
```

## 六、下一步建议（按性价比排序）

1. **接一次真模型跑 10 份样本**，把"模型通道耗时/接受率/误报变化"记成一张表 —— 这是答辩最容易被问、也最容易补的；
2. **用 PROVDATA 训节点④**（有 GPU 的机器上 2 小时），把弱监督换成真监督，论文里就能写"与 PROVBENCH 口径可比"；
3. **补十万份的存储压测**（哪怕只压 1 万份合成件），把"容量目标"变成"实测容量"；
4. 若时间不足，**把申报书按第三节的 8 条改法修订**，比再加功能更能提高可信度。
